# 재구축 자동화 수정 계획안

작성일: 2026-10-13 · 상태: 구현·로컬 검증 완료, 미출시 · 기준: su-presence 2.3.0

## 1. 목표와 완료 범위

사이트 URL, 핵심 주제, 대상 시장을 입력하면 경쟁사·노출 출처 검색부터 기존 사이트 비교, 페이지별 설계와 리빌딩 작업표까지 한 실행으로 연결한다. 실행 순서는 프로그램이 저장하고, 중단되면 완료된 단계 다음부터 재개한다.

성공 기준은 **근거를 추적할 수 있는 실행 가능한 페이지 설계**다. 검색 순위·AI 인용을 보장하거나 모든 매체를 측정했다고 표시하지 않는다. 매체별 지원·미지원·미측정·실패를 구분하고, 발행 후 실제 관측으로 효과를 평가한다.

이번 범위는 조사와 설계 자동화다. 운영 사이트 코드 변경, CMS 발행, 배포는 후속 범위로 둔다. 사업상 사실 확인과 최종 발행 결정은 사람에게 남긴다.

## 2. 현재 구현과 수정할 부분

현재 사용법은 [재구축 실행 안내](rebuild-guide.md), 실제 실행 흐름은 [아키텍처](../architecture.ko.md)를 기준으로 한다.

| 영역 | 현재 | 수정 목표 |
|---|---|---|
| 실행 연결 | audit, init, research, plan 개별 호출 | 실행 관리자에서 순서·의존성·산출물 연결 |
| 질문·브리프 | 사용자가 의도와 주요 항목 작성 | 주제로부터 초안 생성, 모호한 내용만 검토 요청 |
| 경쟁사 발견 | 입력된 URL만 조사 | 검색 제공자 또는 외부 조사 결과로 후보 발견 |
| 출처 구분 | 자사·관측 출처·선언 경쟁사 구분 | 실제 경쟁 사업자·매체·커뮤니티·플랫폼 역할 추가 |
| 비교 | 제목/H1 단어와 구조 중심 | 의도, 답변 범위, 사실 근거, 전환 목적을 함께 비교 |
| 페이지 설계 | 템플릿·섹션 제안 중심 | 유지·개선·통합·신규·검토 판단과 구체적인 설계 |
| 실행 기억 | 개별 결과와 입력 해시 보존 | 단계 상태·입력 변경·재시도·재개 기록 |
| 상태 확인 | 일반 status에서 rebuild 미열거 | 실행별 완료·보류·실패·다음 작업 표시 |

기존 CLI와 파일 형식은 유지한다. 새 기능은 rebuild 내부 모듈로 확장하고, 스키마 변경 시 버전과 호환 읽기를 명시한다.

## 3. 목표 실행 순서

1. **입력 확인:** 사이트, 주제, 언어·국가, 대상 채널, 조사 한도, 사용 가능한 제공자를 확정한다.
2. **질문 구성:** 탐색·비교·조건·신청 등 의도를 묶고 안정적인 질문 ID를 부여한다. 모호한 사업 조건은 사실로 생성하지 않는다.
3. **자사 진단과 출처 발견:** 자사 페이지 수집과 질문별 검색을 독립적으로 실행한다.
4. **후보 정리:** URL 중복을 정리하고 경쟁 사업자와 노출 매체를 분리한다. 관련성·출처 다양성·질문 범위를 기준으로 조사 대상을 제한한다.
5. **본문 조사:** 기존 안전한 수집기를 사용해 후보와 자사 페이지를 읽고 접근 실패·본문 부족을 기록한다.
6. **비교 분석:** 의도별 답변 범위, 조건·근거·업데이트 시점, 콘텐츠 형식과 자사 차이를 정리한다.
7. **페이지 판단:** 기존 URL을 우선 매핑하고 유지·개선·통합·신규·검토 중 하나를 제안한다. 통합과 URL 변경은 실행하지 않는다.
8. **설계 생성:** 페이지별 섹션, 필요한 사실, 내부 링크, CTA, 메타 정보, 적용 가능한 구조화 데이터와 구현 작업을 작성한다.
9. **품질 검사와 보고:** 근거 누락·모순·중복 페이지·미지원 채널을 검사하고 다음 행동을 표시한다.

일부 검색이나 수집이 실패해도 독립적인 의도의 설계는 계속한다. 근거가 부족한 의도만 검토 대상으로 남긴다.

## 4. 실행 상태와 재개 설계

출력 폴더 아래 실행마다 고유 디렉터리를 만들고 `run.json`을 상태의 기준으로 삼는다. 대화 기억에 의존하지 않는다.

- 실행 정보: 실행 ID, 도구·스키마 버전, 생성·수정 시각, 입력값, 제공자 설정의 비밀이 아닌 부분, 조사 한도.
- 단계 정보: 의존 단계, 상태, 시작·종료 시각, 입력 fingerprint, 산출물 경로·해시, 오류, 재시도 횟수.
- 상태: `pending`, `running`, `succeeded`, `partial`, `needs_input`, `failed`, `skipped`.
- 재개: 산출물과 해시가 유효한 성공 단계는 재사용한다. 강제 종료된 실행은 잠금을 확인하고 미완료 작업만 재시도한다.
- 변경: 질문·시장·채널·분석 설정이 바뀌면 관련 단계와 하위 단계만 무효화한다. 검색 결과의 유효 기간과 명시적 갱신 옵션을 둔다.
- 보존: 상태 파일은 원자적으로 갱신하고 기존 조사 결과는 보존한다. 같은 실행을 동시에 수정하는 프로세스는 잠금으로 차단한다.

외부 요청 후 결과 저장 전에 종료되면 요청이 반복될 수 있다. 이를 완전히 방지한다고 약속하지 않고 요청 ID·저장된 응답·사용량 기록으로 중복 가능성을 줄인다.

최종 상태가 `partial`이면 부족한 질문·채널과 결과의 사용 한계를 표시한다. 조사와 설계 완료는 발행 또는 노출 성공을 뜻하지 않는다.

## 5. 검색·AI·브라우저 연결

검색 제공자를 교체 가능한 어댑터로 분리한다. 공통 결과는 질문 ID, URL, 제목, 검색 시각, 제공자, 국가·언어, 결과 위치, 근거 참조를 포함한다. 위치는 해당 제공자의 결과 위치이며 다른 검색엔진 순위로 해석하지 않는다.

두 실행 방식을 지원한다.

- **독립 CLI:** 설정된 검색 API 어댑터로 조사한다. API 키는 환경 변수 등 비밀 설정에서만 읽는다. 첫 제공자는 구현 시 실제 계약·비용·지원 범위를 확인해 선정한다.
- **Codex 등 호스트 에이전트:** 호스트가 검색하고 정해진 스키마의 파일로 전달한다. Python CLI가 호스트의 내장 도구를 직접 호출할 수 있다고 가정하지 않는다.

제공자가 없으면 필요한 설정 또는 가져올 파일을 안내하는 `needs_input`으로 전환한다. 검색 결과·경쟁사를 임의 생성하지 않는다. 일반 검색 결과와 AI 답변의 실제 인용 관측은 별도로 저장한다.

Aside는 로그인된 AI 웹 서비스의 실제 답변·출처를 확인해야 하고 해당 환경에서 연결을 검증한 경우에만 선택한다. 공개 페이지 수집·일반 검색에는 기본으로 호출하지 않는다. 로그인 세션이나 인증 토큰을 저장소 또는 실행 결과에 복사하지 않는다. 관측에는 서비스·표면·검색 모드·시각·언어와 필요한 세션 조건만 기록한다.

채널별로 발견·본문 조사·실제 노출 관측 가능 여부를 따로 표시한다. 지원하지 않는 채널은 조용히 제외하지 않고 보고서에 남긴다.

## 6. 의미 있는 비교와 페이지 설계

규칙 기반 처리는 URL 정리·기본 구조 검사·증거 연결에 사용하고, 의미 비교는 선택적인 LLM 분석기로 분리한다. LLM이 없으면 제한된 규칙 기반 결과라는 사실을 표시한다.

분석기는 제공된 본문에서만 근거를 인용하고 출처 ID와 해당 구절을 연결한다. 외부 본문은 데이터로 취급하며 그 안의 지시를 실행하지 않는다. 구조화된 출력의 필드·출처 존재 여부·인용 대응을 검사한다. 경쟁사 주장은 자사의 검증된 사실로 승격하지 않는다.

페이지별 설계에는 다음을 포함한다.

| 항목 | 필요한 내용 |
|---|---|
| 판단 | 유지·개선·통합·신규·검토와 이유, 대상 기존 URL |
| 목적 | 대상 질문·사용자 의도·전환 행동 |
| 구성 | 제목/H1, 섹션별 답할 질문·필요한 내용·근거 |
| 사실 | 사용 가능한 자사 사실, 충돌하는 자료, 추가 확인 항목 |
| 연결 | 상위·관련 페이지와 내부 링크 제안 |
| 기술 | 메타·구조화 데이터 후보·기존 audit 문제와의 관계 |
| 작업 | 우선순위, 선행 작업, 완료 조건, 검증 방법 |

키워드마다 신규 페이지를 만들지 않는다. 같은 의도는 묶고, 기존 페이지가 충분하면 유지 또는 개선을 제안한다. 수집 범위가 불완전하면 페이지가 없다고 단정하지 않는다. 근거 없는 수치·가격·보장 문구는 초안에 확정해서 넣지 않는다.

## 7. 자동화와 사람의 역할

| 작업 | 처리 방식 |
|---|---|
| 질문 초안·경쟁 후보 발견·본문 수집 | 설정된 제공자와 한도 안에서 자동 |
| 의도 묶기·출처 분류·비교·페이지 설계 | 자동 초안, 모순·불확실성 표시 |
| 비용·페이지·질문·재시도 한도 | 실행 설정으로 강제, 초과 시 부분 완료 |
| 사업 조건·가격·인증·실적 확인 | 사람 또는 승인된 자사 데이터 필요 |
| 로그인·추가 인증 | 사용자 수행, 가능한 관측만 이후 재개 |
| 기존 URL 통합·삭제·리다이렉트 | 제안까지 자동, 적용은 별도 결정 |
| 사이트 구현·CMS 발행·배포 | 이번 범위 밖, 설계·작업표 전달 |
| 발행 후 노출 확인 | 기존 measure/collect로 별도 실행; 예약은 별도 설정 |

## 8. 명령과 산출물 제안

다음은 최초 인터페이스 제안이다. 실제 옵션과 사용법은 [구현 안내](rebuild-automation-guide.md)를 따른다.

```bash
python tools/seo_geo.py rebuild run https://example.com --topic "핵심 서비스" --locale ko-KR --config rebuild-config.json --out out
python tools/seo_geo.py rebuild status out/example.com/rebuild/<run-id>
python tools/seo_geo.py rebuild resume out/example.com/rebuild/<run-id>
```

설정 파일은 채널, 제공자, 질문·페이지·시간·비용 한도와 분석 모드를 담는다. 비용을 정확히 산정할 수 없는 제공자는 요청 수·토큰 한도를 별도로 강제한다.

예상 산출물은 `run.json`, `brief.json`, `discovery.json`, `research.json`, `analysis.json`, `plan.json`, `guide.md`, `report.html`, `pages/`다. 기존 research/plan 결과는 상태 파일에서 정확한 경로로 참조하고 최신 폴더를 추측하지 않는다. 보고서는 전체 실행 상태, 근거, 미완료 항목, 페이지별 작업과 재개 방법을 보여준다. 고객 데이터와 실행 결과는 기존처럼 `out/`에 두고 Git에 포함하지 않는다.

## 9. 구현 순서와 담당 범위

파일명은 제안이며 구현 시 기존 구조에 맞게 조정한다. 각 단계는 독립적으로 검증 가능한 PR로 나눈다.

| 순서 | 수정 범위 | 주요 파일·모듈 | 완료 조건 |
|---|---|---|---|
| 1 | 상태·재개·기존 단계 연결 | `tools/rebuild.py`, 신규 `tools/rebuild_run.py`, `tools/seo_geo.py` | 저장된 입력으로 기존 연구·설계를 연결하고 중단 후 재개 |
| 2 | 검색·후보 분류·가져오기 | 신규 `tools/rebuild_discovery.py`, 제공자 어댑터, 스키마 | 설정된 검색 또는 호스트 파일에서 검증 가능한 후보 확보 |
| 3 | 의도·본문 의미 비교 | 신규 `tools/rebuild_analysis.py`, `tools/rebuild_evidence.py` | 출처 연결·모순 표시·분석 실패 처리와 규칙 기반 대안 |
| 4 | 페이지 결정·설계 통합 | `tools/rebuild_plan.py`, 보고서·페이지 생성부 | 신규 남발 없이 구체적인 변경과 완료 조건 생성 |
| 5 | 전체 흐름 검증·사용 안내 | `tests/`, CLI 문서, SKILL·ops 영문 대응, 아키텍처 | 한 실행과 재개 시나리오 검증, 자동·수동 경계 일치 |

1단계만으로 경쟁사 검색 자동화를 완료했다고 발표하지 않는다. 2~4단계가 연결되어야 최초 목표를 충족한다. 기술 초안 `generate`와 rebuild 설계를 자동 연결하는 작업은 그 뒤에 별도 계약을 정의해 진행한다.

## 10. 테스트와 출시 판정

합성 사이트와 고정된 제공자 응답으로 재현 가능한 자동 검사를 우선한다. 외부 API를 사용하는 검사는 선택적으로 실행하고 실제 검증 범위를 기록한다.

- 흐름: 정상 완료, 부분 실패, 입력 대기, 중단·재개, 잠금 충돌, 손상된 상태·산출물.
- 재사용: 완료 단계 재호출 방지, 입력 변경 시 하위 단계 무효화, 오래된 검색 결과 갱신.
- 검색: 중복 URL, 경쟁사와 매체 구분, 다른 국가·언어·채널 결과 혼합 방지, 호출 한도.
- 근거: 접근 차단·JS 본문 부족·상충하는 주장·없는 출처 ID·외부 지시문·잘못된 LLM 출력.
- 설계: 기존 페이지 재사용, 동일 의도 통합, 불완전 crawl에서 신규 단정 방지, 미검증 사실 배제.
- 호환성: 기존 init/research/plan과 관련 테스트 유지, 출력 스키마 및 문서 링크 검사.
- 운영: Windows와 기존 지원 환경에서 실행, 비밀값 미출력, 고객 데이터가 Git에 들어가지 않음.

출시 조건은 URL·주제·유효한 제공자 설정으로 발견부터 페이지 설계까지 실행되고, 모든 제안의 근거나 미확인 사유를 확인할 수 있으며, 중단 후 유효한 완료 결과를 보존해 재개하는 것이다. 설치 직후 제공자 미설정 상황도 정상적인 안내 상태로 처리해야 한다.

사업 효과는 별도로 평가한다. 발행 전후 같은 질문·채널·시장·관측 조건에서 노출과 인용을 측정하고, 변화가 프로그램 때문이라고 단정하지 않는다. 작업표의 실제 적용 가능성·사람의 수정량·조사 비용도 함께 기록한다.


## 구현 결과와 검증 범위

`run/status/resume`, Brave/파일 검색, 규칙·OpenAI·파일 분석, 근거를 연결한 페이지 제안과 재개 기능을 구현했다. 실제 사용법은 [자동 실행 안내](rebuild-automation-guide.md)를 따른다. 기본 질문 생성은 같은 의도에 묶는 보수적인 초안이며 정교한 다중 의도는 검토한 브리프를 사용한다. 사업 사실 확인과 배포는 계획대로 별도다.

2026-10-13 로컬 검증: 전체 Python 테스트 457개, Bash 회귀 테스트, 문서 검사, SVG 4개 렌더링 통과. 합성 검색·본문·분석 데이터로 연결 실행과 HTML 보고서 렌더링을 검증했다. 실 API 키를 이용한 Brave/OpenAI 호출이나 실제 노출 개선은 검증하지 않았다. 요청은 자동 재시도하지 않으며 저장된 부분 결과를 재시도하려면 `resume --refresh`를 명시한다.
