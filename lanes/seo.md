# SEO — 기술 토대, 항목별 점검

검색엔진과 각 서비스가 안정적으로 가져오고 이해할 수 있는 콘텐츠가 목표다.
핵심 본문·메타를 원시 HTML에도 제공하면 렌더링 지원이 다른 크롤러의 접근성과 장애 복원력이 좋아진다.

이 레인은 여러 검색·생성 엔진의 발견 가능성을 높이는 공통 토대다. Google Search 기반 AI 기능은
일반 검색 색인과 snippet 적격성을 사용하므로 Googlebot 접근과 색인 상태를 함께 확인한다.

## 1. 크롤러 눈에 실제로 보이는 것

- [ ] 핵심 페이지가 **비로그인으로 열리는가?** 로그인 월 뒤 콘텐츠는 색인되지 않는다.
      전부 열기 어려우면 티저(첫 문단·핵심 수치)라도 SSR로 열고 나머지를 게이트한다
- [ ] `curl -sL <url>` HTML에 핵심 본문이 있는가? SPA/CSR이면 SSR·SSG·프리렌더를 검토한다.
      Google은 JavaScript를 렌더링할 수 있으므로 원시 본문이 적다는 사실만으로 색인 불가를 확정하지 말고,
      렌더링 결과와 Search Console도 확인한다. 원시와 렌더를 비교할 항목과 보고 방식은
      [렌더 비교](../ops/evidence.md#javascript-렌더-비교--원시와-렌더를-나란히)를 따른다
- [ ] ⚠️ **CSR 바일아웃 함정**: SSR 프레임워크에서도 특정 훅·API가 페이지를 통째로 클라이언트
      렌더로 떨어뜨릴 수 있다 (Next.js의 Suspense 없는 `useSearchParams` 등).
      **배포마다 대표 페이지를 curl로 재확인하라** — 본문 글자 수가 갑자기 줄면 사고다

## 2. noindex 사고 점검 (최우선)

```bash
curl -sL  https://example.com | grep -oiE '<meta[^>]*robots[^>]*>'
curl -sIL https://example.com | grep -i 'x-robots-tag'
```
스테이징용 `noindex`의 프로덕션 배포는 다른 모든 작업을 무효로 만든다.
메타 태그와 **HTTP 헤더 둘 다** 봐야 한다.

## 3. 사이트맵

- [ ] sitemap.xml이 실제로 응답하는가, robots.txt의 `Sitemap:` 줄이 그 주소를 가리키는가
- [ ] 개별 상세 URL(제품·글·항목)이 **하나도 빠짐없이** 실려 있는가 — 목록 페이지만 넣고
      끝내는 사고가 가장 흔하다
- [ ] 5만 URL·50MB 초과가 보이면 **미리 샤딩** (sitemap index + 파트 분할).
      한도 초과 순간 전체가 조용히 무시된다
- [ ] 새 콘텐츠 유형을 만들면 **사이트맵에 넣는 것까지가 출시다**. 빼먹은 유형은 몇 달씩
      색인 밖에 있게 된다

## 4. 메타

- [ ] 제목 영문 50~60자 / **한글 25~30자**: 핵심 키워드 앞쪽, 브랜드 뒤쪽
- [ ] 설명 영문 150~160자 / **한글 70~80자**: 클릭할 이유가 있는 문장
      (면책·경고 문구를 넣지 마라 — CTR만 죽인다)
- ℹ️ 기준은 글자 수가 아니라 **검색결과에 표시되는 폭**이다. 한글은 한 글자가 영문의 약
      두 배 폭이라 영문 기준을 그대로 쓰면 잘린다. 혼합 문구면 짧은 쪽에 맞춰라
- [ ] ⚠️ 길이를 잴 때 **바이트가 아니라 글자 수로** 재라. bash `${#var}`는 UTF-8에서
      바이트를 세므로 한글 1자가 3으로 잡힌다 — `printf '%s' "$t" | wc -m`을 써라
- [ ] 제목·설명은 페이지의 고유한 내용을 설명해야 한다. 반복 문구는 개선 신호지만,
      그것만으로 중복 콘텐츠가 확정되지는 않으므로 본문·canonical도 함께 확인한다
- [ ] OG 이미지: 링크가 공유될 때 노출되는 첫인상이다. 페이지 유형별로 자동 생성해두면 가장 낫다

## 5. 구조화 데이터 (JSON-LD)

- [ ] 구조화 데이터는 검색·AI 노출의 필수 조건이 아니다. 페이지에 실제로 존재하는 유형에 맞춰
      Article, Product, FAQPage, BreadcrumbList, Organization, LocalBusiness 등을 선택한다
- [ ] 사용자가 보거나 확인할 수 있는 내용을 정확히 표현한다. 공백·표현 차이보다 의미와 핵심 값의
      일치가 중요하며, 화면에 없는 허위 내용을 넣지 않는다
- [ ] `@id` 운용: 하나의 엔티티에는 사이트 전역에서 @id 하나만 쓴다. 페이지마다 Organization을
      새로 선언하면 엔티티가 분열된다 (LLMO 레인에 직접 타격) — 전역 1회 선언 + 참조
- [ ] 검증: Google Rich Results Test 또는 schema.org validator로 **배포 후** 확인

## 6. URL·응답 위생

- [ ] canonical: 쿼리 파라미터가 붙은 변형과 중복 경로 전부가 정본 URL 하나를 지목하게 한다
- [ ] 다국어 사이트면 hreflang을 양방향으로 건다 — A만 B를 가리키고 B가 A를 안 가리키면
      그 선언은 통째로 무시된다
- [ ] 없는 페이지는 200이 아니라 404 — soft 404는 색인 예산을 태운다
- [ ] ⚠️ **404 베이크 함정**: ISR·CDN 캐시에서 일시 장애의 404가 몇 시간씩 구워질 수 있다.
      데이터 조회 실패 시 404 대신 throw(재시도)하라 — "없음"과 "못 가져옴"은 다르다
- [ ] 리다이렉트는 최대 1번에 끝나야 한다 — 2홉부터 크롤 예산과 링크 신호가 새어 나간다

## 7. 성능·자산

- [ ] 이미지는 WebP/AVIF로 내보내고 width/height를 속성으로 박아둔다 — 빠지면 로딩 중
      레이아웃이 밀려 CLS를 깎아먹는다
- [ ] LCP를 결정하는 자원(첫 화면 이미지·본문 폰트)은 preload로 먼저 당겨온다
- [ ] 로고·아이콘 무손실 최적화 — 수백 KB 로고가 전 페이지에 실리는 낭비가 흔하다

## 8. 색인 가속

- [ ] IndexNow: 새·갱신 페이지를 발행 즉시 핑 (Bing·네이버·Yandex 계열이 소비)
- [ ] Google은 IndexNow 미지원 — 사이트맵 `lastmod` 정확성으로 승부
- [ ] 대량 발행 시 **핑을 발행 파이프라인에 내장하라** — 손으로 하는 핑은 반드시 끊긴다
